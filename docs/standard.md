# Model-to-IDA interface specification

Proposal v0.1 defines how an investigative model requests evidence, changes an
IDA database, and receives a result that can be checked. The model interprets
the code. The host identifies targets, controls writes, verifies database state,
and enforces the requirements of a selected investigation scope.

**Must** marks a contract requirement; **should** marks a recommendation.
Implementation notes describe the scope supported by this release.

## Evidence and identity

The host must advertise available queries and edits, their required fields,
limits, and errors. Paged results must expose counts and continuation state.
The reference interface uses `total`, `has_more`, and revision-bound cursors
for its pageable queries.

Evidence must identify the binary component and database revision it came from.
Each component has an input hash and its own IDB. A target reference identifies
an object within that component. Local-variable references must distinguish the
variable; call references must distinguish the callsite. A bare address is
insufficient because different binaries can use the same address.

Function summaries, disassembly, pseudocode, cross-references, types, and binary
metadata are separate query surfaces. Historical evidence and model inferences
must be labeled accordingly. Additional inspection is available through
read-only IDAPython on a disposable database.

Exact type lookup and comparison use IDA's type system. A similar printed name
or matching memory offset can suggest where to look; neither establishes that
two types are equivalent or that an access belongs to a particular field.
Results must distinguish IDA-confirmed references from candidates and report
incomplete scans. A partial search with no matches cannot establish absence.

Edits must cite host-recorded evidence for the current target and revision.
The host must reject stale or mismatched references and explain how to obtain
valid ones. This implementation expires evidence whenever its component
revision changes, so even an unrelated annotation can require reinspection.
It does not yet track dependencies finely enough to reuse unaffected evidence.

## Edits and receipts

The host must retain the requested change, supporting evidence, observed
result, and acceptance decision. A **receipt** is the per-operation record of
these checks, including errors and recovery guidance.

The model submits an edit kind, value, `target_ref`, and evidence references.
The host adds an operation ID, the database revision, and target identifiers
obtained from IDA before sending the request to the worker.

| Machine contract | Contents |
| --- | --- |
| [Operation](../schemas/verified_ida/v1/operation.schema.json) | One fully identified edit and its preconditions |
| [Batch](../schemas/verified_ida/v1/operation_batch.schema.json) | A group of operations sent to an IDA worker |
| [Receipt](../schemas/verified_ida/v1/receipt.schema.json) | Execution stage, readback, persistence status, errors, and recovery information |

These checked-in schemas describe the host-to-worker boundary. The model sees
the smaller tool definitions generated by `model_tools.py` and the live
capability manifest in `query_contract.py`. Schema `$id` URLs identify the
contracts; no remote schema registry is needed at runtime.

The contracts cover function names, comments and prototypes; locals, globals
and named types; and relationships. Two additional worker operations,
`address.comment.set` and `function.folder.set`, are used in conformance
fixtures and are not exposed through `edit_ida`. Runtime validators live in
`contracts.py`; regression tests compare their enums with the schemas.
The host fills `work_item_id` with the active reconciliation finding's ID,
or `null` for an unscoped edit.

### Application, persistence, and recovery

The accepted database must remain protected while a proposed edit is checked.
The reference host applies one edit to an isolated candidate IDB, reads the
result through a separate path, and checks the relevant effects before making
the candidate the accepted database. A failed candidate is not promoted; the
failure is recorded for inspection and retry.

Prototype, local-type, global-type, and named-type edits also receive a
comparison of affected IDA state. IDA may import supporting types as part of a
valid edit; unrelated changes require rejection. Unavailable measurements must
be reported explicitly. For example, a caller that Hex-Rays cannot decompile
can prevent a type change from being verified. Other edit kinds do not receive
this full comparison of changes beyond the requested target.

Promotion must be recoverable after interruption. Packed-IDB replacement and
SQLite commit are separate atomic steps. Recovery compares the database bytes
with recorded hashes, reconciles the ledger, and rolls back an uncommitted
promotion. If it cannot determine the valid state, it stops for intervention.

Checkpoints must reopen affected IDBs in a fresh process and test that accepted
changes persisted. Receipts must record mechanical verification separately
from semantic review.

## Feedback and investigation state

A failed operation must return its target, stage, requested and observed state,
error, and a specific recovery direction. Retries must preserve prior failures.

Post-edit feedback should identify relevant consequences and incomplete
annotations. Examples include a renamed function without a behavior comment
or parameters that retain generated names. The implementation uses native IDA
name provenance where available and distinguishes heuristics from measured
facts.

Checks on an edited function are not suppressed by its name or size. Type-use
feedback reports whether its measured surfaces were scanned completely; missing
scan metadata is uncertainty, not proof that the type is unused.

Required work and advisory inventory must remain distinct. Inspecting an
inventory does not make every entry an obligation. Required items retain their
status until an accepted correction or documented decision resolves them.

The project separates accepted analysis, operational history, and working notes:

- IDBs hold accepted names, comments, interfaces, types, and relationships.
- The SQLite ledger holds inspections, operations, receipts, revisions,
  checkpoints, and tracked investigation work. Independent review also saves
  its findings, decisions, and consistency assessments in a separate review
  disposition ledger.
- The notebook holds the current understanding, uncertainties, next actions,
  and a chronological investigation journal.

The notebook's current-state sections are rewritten as understanding changes,
while the journal preserves important revisions. Notebook entries do not replace
IDA annotations or operation records. The [output guide](usage.md#inspect-and-share-results)
lists the files needed to inspect or resume a project.

Compaction must preserve these records and valid tool-call/result pairs.
The runner retains saved conversation state and makes current instructions
and project state available after context reduction. Subsequent edits still
require current IDA evidence.

## Components and enforceable scope

Recovered executable components must retain their byte identity, extraction
provenance, parent link, and independent IDB. Before following a child, the
investigator should record the parent's relevant findings and how it uses the
child. Switching components must preserve target identity.

The host should support deeper investigation of a selected claim. An enforced
scope must identify its targets and completion requirements. The host checks
whether the required code was inspected, decisions were recorded, and the
original claim was revalidated. The model decides what the evidence means.

The experimental `--coverage-reconciliation` profile freezes up to eight
findings with up to twelve targets each. Within a selected scope, statically
decoded direct calls can require downstream inspection followed by revalidation
of the parent claim. A supported terminal boundary ends that traversal.
This enforcement excludes indirect calls, virtual dispatch, callbacks, tail
calls, and whole-program annotation. Ordinary independent-review edits do not
open these mandatory call-flow scopes.

## Independent review and closure

Independent review checks whether the IDA project supports the investigation's
conclusions and identifies important work still to be done. It follows four
stages, leaving the primary investigation's IDBs unchanged.

### 1. Gather evidence

The host builds a deterministic inventory of annotations and possible gaps.
Model reviewers use that inventory and read-only access to IDA to examine
individual claims and the overall explanation of the program. Each supported
finding identifies the functions, data, or components that need attention.

Reviewers must work on disposable database copies. The host compares their
annotations and types before and after each collection stage to check for
changes. Findings must cite evidence retrieved during that stage; older
citations serve as history. Review packets include both repeatable and
nonrepeatable function comments and mark any truncated text.

### 2. Define the work

The host validates the findings and freezes the correction scope. It then
resumes the saved investigator in a separate review project. Unrelated
discoveries go into an advisory backlog, keeping the required work finite.

Before an edit, targets must be checked against current IDA state. A suspected
relationship that IDA cannot confirm as a direct call remains a question about
its two endpoint functions. A global-data edit must identify the start of a
data item recognized by IDA.

### 3. Address each finding

The investigator works through one finding at a time. It inspects the relevant
code, decides what the evidence supports, and updates IDA and the notebook.
This unit of work is an **application wave**. Its recorded outcome, or
**disposition**, can be to apply the proposed correction, revise and apply it,
reject it, defer it, or request a specific follow-up target.

Some findings require recovering embedded code or data. The request must
identify the parent byte range and the question the recovery should answer.
The recovery service retains validated bytes and their provenance. Data that
cannot be loaded as a program stays linked to its parent; loadable artifacts
receive a child IDB, with additional edit authority limited to that child.

Review tracks recovered artifacts and IDB edits separately. Retaining the bytes
establishes a successful recovery; the investigator must still assess whether
the evidence answers the question. Verified partial edits are preserved while
the unfinished part remains tracked.

### 4. Check completion

After updating the notebook, the investigator must check that accepted review
conclusions agree with the annotations. A conflict with an earlier edit from
the same review is recorded with its current operation ID, related finding,
explanation, and fresh evidence.

The host marks the conflict as high priority and allows one automatic correction
pass. Corrections are limited to the recorded edit's target and annotation
kind, including the exact comment slot. The investigator can correct or qualify
the annotation, reject the newer interpretation, or record unresolved
uncertainty. It then repeats the consistency assessment. Any remaining
disagreements prevent analytical completion.

Closure also requires persistence checks and an accounting of required findings.
High-priority deferrals and unresolved mechanical failures can block it. For
example, a missing payload delivered at runtime can leave the analysis
incomplete even when all other required work is finished.

The completion report must state what was verified, what remains unresolved,
and whether the selected completion policy was satisfied. A budget limit must
be reported as a stop, with unfinished work preserved. Resumption must retain
the findings, targets, edits, decisions, notebook, budget settings, and usage.

The consistency assessment is a recorded model judgment about the reviewed
work. Its evidence remains available for inspection; other errors may still
exist elsewhere in the project.

## Reference implementation

The runner uses the OpenAI Agents SDK and serialized access to IDA through
repository-owned workers. A persistent disposable session serves queries;
separate candidates receive edits; packed component IDBs hold accepted state.
The [user guide](usage.md) lists the tested environment and deployment steps.
