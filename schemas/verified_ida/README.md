# Verified IDA machine contracts

The files under `v1/` describe the canonical host-to-IDA mutation boundary.
They are protocol artifacts, but they are not the raw request format
shown to the model.

The checked-in files are authoritative. Their HTTPS `$id` values provide a
stable namespace and do not imply that a remote schema registry is required at
runtime.

| Schema | Role |
|---|---|
| `operation.schema.json` | One atomic, fully bound IDA mutation. The host supplies artifact identity, revision, target anchors, and operation identity. |
| `operation_batch.schema.json` | The trusted worker's transport envelope for one or more canonical operations. The model-facing API still submits one semantic edit at a time. |
| `receipt.schema.json` | Complete per-operation outcome, including execution stage, exact observed state, persistence state, errors, and recovery guidance. |

The model instead receives the smaller tool schemas generated by
`src/verified_ida/model_tools.py` and the live capability manifest generated by
`src/verified_ida/query_contract.py`. The model supplies semantic intent and an
opaque target reference; the host constructs and validates the canonical
operation.

The canonical operation vocabulary is slightly broader than the current
model-facing edit vocabulary. `address.comment.set` and `function.folder.set`
remain trusted worker operations used by conformance fixtures but are not
advertised through `edit_ida`. A conforming host must not imply that an
internal operation is model-accessible unless it appears in the live mutation
capabilities.

The Python constants and validators in `src/verified_ida/contracts.py` are the
reference implementation. Focused tests require the checked-in schema enums to
match those runtime contracts.

The runtime uses SQLite operations, receipts, frontier records and notebook
metadata instead of a model-maintained campaign ledger. The nullable `work_item_id` field remains in v1 operations and receipts
for unscoped operations. During an active experimental reconciliation finding,
the host supplies that finding's identifier to bind the mutation to its work
item; outside that context it supplies `null`.
